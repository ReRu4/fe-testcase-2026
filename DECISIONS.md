# PokeMap Widget — принятые решения

Этот документ фиксирует архитектуру, трактовку неоднозначных требований и
критерии готовности. По мере реализации он будет дополнен фактическими
ограничениями, результатами проверок и командами запуска.

## 1. Границы решения

- Виджет реализуется на React 18, TypeScript в режиме `strict` и MapLibre GL JS
  без React-обёрток над картой.
- Production-артефакт `dist/pokemap-widget.js` — один самодостаточный синхронно
  подключаемый JS-файл в формате IIFE. React, MapLibre и стили входят в него.
- Зафиксированы React 18.3.1, MapLibre GL JS 6.3.0, TypeScript 5.9.3 и Vite
  7.3.6. Точные версии хранятся в `package-lock.json`.
- Данные загружаются напрямую из Wikipedia GeoSearch, карта использует стиль
  OpenFreeMap Liberty. Собственный сервер не создаётся.
- Прогресс хранится только в браузере.
- `host-page.html` и файлы каталога `host` не изменяются. Для разработки будет
  использоваться отдельная демо-страница, а исходный host — как интеграционный
  стенд.
- Недокументированный `window.__widgetHostCompat` не используется: он отключает
  проверяемый `transform` и, согласно host-стенду, отсутствует в production.

## 2. Трактовка требований

### Источник данных

Во вводном абзаце упомянуты точки из OpenStreetMap, но раздел «Данные» и
`docs/DATA.md` однозначно задают Wikipedia GeoSearch. Поэтому точки берутся из
Wikipedia, а OpenFreeMap/OSM используются как картографическая подложка.

### Положение игрока

Маркер игрока закреплён в центре карты. Игрок перемещается панорамированием
карты; после завершения движения координаты центра становятся координатами
игрока. Кнопка «Я здесь» использует `navigator.geolocation` и перемещает карту к
полученной позиции. Отказ в доступе или отсутствие API показываются внутри
виджета и не приводят к ошибке всего приложения.

### Сбор точки

- Сбор выполняется автоматически после завершения перемещения игрока.
- Доступна точка на расстоянии `<= collectRadiusMeters`; значение по умолчанию —
  50 метров.
- Если одновременно доступны несколько точек, они собираются по расстоянию от
  ближней к дальней, а при равном расстоянии — по стабильному ID. Это делает
  начисление комбо воспроизводимым.
- Уже собранный ID игнорируется при последующих проверках.

### Начисление очков и комбо

- Для сбора сначала вычисляются `floor(базовые очки * текущий множитель)`, затем
  множитель увеличивается на `0.2`, но не выше `3.0`.
- Множитель хранится как целое число шагов, а не как `float`, чтобы избежать
  накопления ошибок вида `1.2000000002`.
- Обычный сбор запускает десятисекундный срок жизни комбо заново.
- Сбор `epic` или `legendary` останавливает этот срок на 30 секунд. После
  разморозки у игрока остаётся полный десятисекундный интервал. Итого, если
  новых сборов не было, сброс произойдёт через 40 секунд после такой точки.
- Обычный сбор во время заморозки обновляет комбо и оставляет полный
  десятисекундный интервал после разморозки. Новый `epic`/`legendary` продлевает
  заморозку до 30 секунд от момента нового сбора.
- Временные состояния описываются абсолютными timestamp. После возврата на
  вкладку или перезагрузки просроченное комбо корректно сбрасывается без
  постоянно работающего фонового `setInterval`.

### Прогресс

Счёт и собранные точки являются общими для пресетов городов. Стабильный ключ
точки включает источник и `pageid`, поэтому одинаковые числовые ID из разных
`apiBaseUrl` не конфликтуют.

## 3. Архитектура

Код разделяется на независимые слои:

1. `entry` — экспорт глобального API и автоматическое обнаружение слотов;
2. `widget` — создание изолированного DOM-корня и React root;
3. `map` — единственное место, управляющее императивным API MapLibre;
4. `data` — запросы Wikipedia, проверка ответа, кэш и преобразование данных;
5. `game` — чистые функции расстояния, доступности, сбора, очков и комбо;
6. `storage` — версионированная сериализация прогресса;
7. `ui` — React-компоненты, не содержащие сетевой или MapLibre lifecycle.

Игровые правила не зависят от React и MapLibre. Благодаря этому их можно
проверять обычными unit-тестами и восстанавливать из хранилища без создания
карты.

## 4. Интеграция в чужую страницу

### DOM и стили

`mount` добавляет в host-элемент ровно один корневой элемент. В нём создаётся
Shadow DOM, куда помещаются React root и локальные стили приложения вместе со
стилями MapLibre. Это защищает виджет от глобальных правил host-страницы
(`box-sizing: content-box`, `img/canvas { max-width: 100% }`) и не выпускает
стили виджета наружу.

В интерфейсе не используются порталы в `document.body` и `position: fixed`.
Popup, карточки и уведомления остаются внутри локального позиционируемого корня,
поэтому не перекрывают шапку конструктора и не меняют соседние блоки.

### Публичное API и экземпляры

Бандл экспортирует `window.PokeMapWidget`:

```ts
interface PokeMapWidgetApi {
  readonly version: string;
  mount(target: string | HTMLElement, config?: PokeMapConfig): PokeMapHandle;
  unmount(handle: PokeMapHandle): void;
}
```

- Строковый target разрешается через `document.querySelector`; отсутствие
  элемента приводит к понятной синхронной ошибке.
- Связь `HTMLElement -> handle` хранится отдельно от DOM-атрибутов host.
- Повторный `mount` в тот же элемент возвращает существующий handle и не
  применяет новый config скрытно.
- Повторный `unmount` безопасен и ничего не делает.
- Удаление host-узла из документа приводит к автоматическому `unmount`.

Один глобальный `MutationObserver` следит только за добавлением и удалением
поддеревьев. Он монтирует новые `[data-widget="pokemap"]` и освобождает удалённые
экземпляры. Ресурсы карты и приложения всегда принадлежат конкретному handle.

### Очистка ресурсов

Каждый экземпляр имеет единый идемпотентный `dispose`, который:

- отменяет незавершённые запросы;
- отключает `ResizeObserver` и локальные подписки;
- отменяет timeout и `requestAnimationFrame`, если они были запущены;
- вызывает `map.remove()`, освобождая обработчики и WebGL-контекст;
- размонтирует React root и удаляет созданный DOM-корень.

Слушатели на `window`/`document` внутри экземпляра допускаются только при наличии
симметричного удаления. Предпочтение отдаётся событиям MapLibre и observers.

ReactDOM 18 при создании первого root один раз устанавливает общий обработчик
`selectionchange` на `document`. Он не принадлежит конкретному экземпляру и не
имеет публичного API для безопасного удаления; попытка удалить его через
внутренности React может сломать другой React-код host-страницы. Поэтому виджет
не вмешивается в этот общий обработчик. На исходном стенде он даёт постоянное
`+1` до снятия baseline, но после baseline пять пересборок сохраняют дельту `0`.
Собственных слушателей на `window`/`document` runtime не создаёт.

## 5. MapLibre и геометрия host-страницы

Карта создаётся один раз после появления её контейнера. React передаёт ей новые
данные и команды через узкий адаптер; экземпляр MapLibre не хранится в React
state.

- `ResizeObserver` отслеживает реальный контейнер, поскольку сворачивание
  боковой панели не вызывает `window.resize`.
- Событие `cms:layout-changed` рассматривается только как дополнительная
  подсказка: корректность не должна зависеть от CMS-специфичного события.
- Масштаб предков определяется по отношению экранного размера элемента к его
  layout-размеру. После стабилизации геометрии вызывается `map.resize()`.
- MapLibre 6.3 сам переводит координаты указателя из экранных пикселей в
  локальные: его `DOM.mousePos` делит смещение на отношение
  `getBoundingClientRect()` к `offsetWidth/offsetHeight`. Поэтому виджет не
  подменяет нативные события и не зависит от внутренних обработчиков карты.
- Pixel ratio карты равен `devicePixelRatio * CSS scale`, поэтому размер backing
  buffer совпадает с фактическим экранным размером canvas. Значение ограничено
  сверху `3`, чтобы режим 125% на HiDPI-экране не создавал чрезмерный WebGL
  framebuffer.
- `ResizeObserver` отслеживает layout-размер, а локальный `MutationObserver` —
  изменения `class/style` у составной цепочки предков, включая выход из Shadow
  DOM. Оба observer и запланированный RAF удаляются до `map.remove()`.

В dev-режиме `maplibre-gl` исключён из Vite dependency pre-bundling: иначе
оптимизатор Vite 7 теряет `maplibre-gl-worker.mjs`. Library-сборка по-прежнему
включает MapLibre и его worker в единственный IIFE-файл.

Точная реализация компенсации считается готовой только после проверки кликов,
перетаскивания, размеров и резкости в режимах 80%, 100% и 125% исходного
host-стенда.

## 6. Слой данных

Ответ внешнего API сначала имеет тип `unknown`. Собственные type guards проверяют
только необходимые поля и пропускают корректные записи, даже если часть страниц
в ответе повреждена.

Преобразование выполняется в таком порядке:

1. проверить `pageid`, заголовок и конечные числовые координаты;
2. исключить типы `country`, `adm1st`, `adm2nd`, `adm3rd`, `city`, `waterbody`,
   `river`, `event`;
3. нормализовать URL миниатюры и описание;
4. вычислить редкость первым подходящим правилом из `docs/DATA.md`;
5. дедуплицировать по ключу источника и `pageid`.

Ключ точки имеет формат `origin + pathname + # + pageid`, например
`https://ru.wikipedia.org/w/api.php#123`. Параметры запроса в ключ не входят:
смена `uselang` не должна превращать ту же статью в новую игровую точку.

Один запрос GeoSearch охватывает радиус 10 км и получает не более 500 страниц.
Центры запросов привязываются к сетке с шагом `0.06°`. Успешные ответы хранятся
в LRU-кэше из 24 ячеек; наружу репозиторий возвращает объединённый набор всех
сохранённых ячеек с дедупликацией по стабильному ID.

Запросы выполняются после `moveend`, с коротким debounce. Область просмотра
разбивается на стабильные пространственные ячейки; загружаются только
отсутствующие ячейки. Предусмотрены:

- ограничение числа параллельных запросов;
- `AbortController` при уничтожении экземпляра;
- дедупликация одинаковых активных запросов;
- LRU-предел памяти;
- повтор запроса только для временных сетевых/серверных ошибок;
- сохранение последних успешных данных на карте при ошибке следующего запроса.

Фактический предел параллелизма — один запрос: переход в другую незагруженную
ячейку отменяет предыдущий, а одинаковые одновременные обращения используют
один `Promise`. Выполняется один повтор через 300 мс для сетевого `TypeError` и
HTTP `408`, `429`, `500`, `502`, `503`, `504`. Остальные HTTP-ошибки, битый JSON
и ошибка в payload Wikipedia не повторяются. Отмена также прерывает ожидание
перед повтором и не очищает ранее заполненный кэш.

Запросы не отправляются на слишком далёких масштабах, где ответ из 500 записей
не может репрезентативно описать весь экран. Пользователь получает понятную
подсказку приблизить карту. Фактическая граница — zoom `11`; после `moveend`
используется debounce 250 мс. Переход ниже границы отменяет текущую загрузку,
но не убирает уже показанные точки.

## 7. Рендеринг и производительность

Точки не создаются как отдельные React-компоненты или DOM-маркеры. Они попадают
в один GeoJSON source и отображаются MapLibre-слоями:

- базовые circle/symbol-слои кодируют четыре редкости;
- доступность и факт сбора задаются feature properties и выражениями стиля;
- hit testing выполняется через `queryRenderedFeatures`;
- обновление source группируется и происходит не чаще одного кадра.

Source `pokemap-pois` хранит только координаты, стабильный ID и редкость. Один
circle-слой кодирует четыре редкости одновременно цветом и размером, второй
слой рисует рамку выбранной точки. Клик обрабатывается делегированным событием
MapLibre по ID слоя, после чего полные данные берутся из `Map<string, Poi>` и
показываются в локальной карточке с миниатюрой и ссылкой на Wikipedia.

Предварительный проектный предел — около 20 000 накопленных точек и до 10 000
одновременно видимых точек на типичном настольном устройстве. Это не результат
замера и будет уточнено после реализации. При превышении предела следующий шаг —
кластеризация на низких zoom, перенос подготовки GeoJSON в Worker, а для
существенно больших наборов — серверные vector tiles вместо одного GeoJSON.

## 8. Дополнительный модуль

Выбран переключаемый heatmap-слой плотности точек.

Причины выбора:

- он повторно использует уже загруженный GeoJSON и не добавляет API-ключ или
  второй источник отказов;
- демонстрирует управление несколькими MapLibre-слоями и их порядком;
- хорошо показывает пользу GPU-рендера на плотных данных.

Heatmap располагается над подложкой, но под интерактивными маркерами игрока и
точек. Скрытие слоя меняет visibility существующего слоя, не пересоздавая карту.

## 9. Публичные события

`onEvent` получает discriminated union. Callback пользователя вызывается через
защищённую обёртку: его исключение не должно ломать жизненный цикл виджета.

```ts
type PokeMapEvent =
  | { type: 'ready'; city: string }
  | { type: 'loading'; active: boolean }
  | { type: 'points-loaded'; received: number; total: number }
  | {
      type: 'collected';
      pointId: string;
      title: string;
      rarity: Rarity;
      awarded: number;
      score: number;
      combo: number;
    }
  | { type: 'city-changed'; city: string }
  | { type: 'progress-reset' }
  | { type: 'error'; source: 'map' | 'data' | 'geolocation' | 'storage'; message: string };
```

`ready` означает, что карта загрузила стиль и основные обработчики установлены;
он не обещает, что Wikipedia уже ответила.

## 10. Хранилище

В `localStorage` записывается объект с обязательной версией схемы. Чтение
выполняется через `try/catch` и runtime-проверку каждого поля. Повреждённая или
неизвестная версия отбрасывается с восстановлением пустого прогресса.

Запись содержит только доменные данные: счёт, шаг комбо, временные отметки и
массив ключей собранных точек. Объекты API, URL изображений и экземпляр карты не
сохраняются. Сброс удаляет запись и атомарно возвращает активный экземпляр в
начальное состояние.

## 11. Проверки и критерии готовности

### Unit-тесты

- классификация всех редкостей и приоритет правил;
- фильтрация запрещённых и частично повреждённых записей;
- Haversine и границы `49.999 / 50 / 50.001` метра;
- начисление очков до увеличения множителя;
- максимум `x3.0`, reset, freeze, продление freeze и восстановление по времени;
- несовместимая/повреждённая версия хранилища;
- дедупликация, кэш и отмена запросов.

### Интеграционные проверки

- синхронная загрузка бандла до появления слота;
- идемпотентный ручной и автоматический `mount`;
- пересборка блока и `stress-test x5` без роста диагностических счётчиков;
- один дочерний корень в каждом слоте;
- освобождение canvas и WebGL после `unmount`;
- изменение ширины при открытии/закрытии панели;
- точные клики и drag, локальные overlay и резкий canvas при 80/100/125%;
- переключение Москвы и Санкт-Петербурга без перезагрузки;
- работа последнего успешного набора точек при ошибке Wikipedia.
